One million chessboards, in OCaml

A server-authoritative world of 64 million squares, a 25×25 snapshot cache and a binary WebSocket protocol.

23 November 2026 6 min read OCaml · Systems

I wanted a project where the interesting constraint was memory rather than features. One Million Chessboards is a 1,000 × 1,000 grid of chessboards: 64 million squares and 32 million starting pieces, all visible from a browser you can pan around.

The server owns the world. The client is a Brr/WASM grid that asks for 25 × 25-board windows, renders them on a canvas, and applies live moves as they arrive over a binary WebSocket protocol. The whole thing is one OCaml binary and a static client.

The state is the design

The naive representation is an object per square, or a record per board. At this size that is not a memory problem, it is a cache-miss generator. The implementation uses flat arrays and packed 64-bit values, with a compact ledger for the move state.

A board is 64 int64 values — one per square — which comes to 512 MB for the full world. The ledger adds about 16 MB. The measured resident set after startup is around 520–525 MB, including the OCaml runtime and benchmark allocations. That number is the reason for most of the other decisions: no per-piece objects, no pointer-chasing across a million boards, and a single authoritative writer so board operations do not need locks.

The cache is the interesting part

Sending the visible region as JSON would be pleasant to debug and hopeless at this scale. Snapshots instead carry one byte per piece. The client keeps a 25 × 25-board window and fetches only the boards it does not already have. Each board snapshot has a revision, so a live move can be applied on top of a cached board without a full refetch.

That introduces the fun failure modes: duplicate events, gaps in the event stream, a move arriving while a snapshot is in flight, and a client that reconnects halfway through a drag. The server is authoritative, so the client's job is to converge on the server's version of the board rather than to guess. Move broadcasts are batched — a 1 ms window and kind-4 4 KiB frames by default — because sending one frame per move across dozens of subscribers wastes more time in the socket layer than in the engine.

One writer, many readers

All mutations go through a single Lwt worker. That removes fine-grained locking from the hot path, but it makes the queue and the broadcaster the parts worth measuring. The server exposes separate timings for receive → submit, worker queue, engine, commit → broadcaster, broadcast wait, recipient lookup, encoding, outbox enqueue, WebSocket write and end-to-end delivery.

The WebSocket layer needed a small patch to httpun-ws for failed writes. A headless browser that disappears mid-frame should not leave the server wedged; the teardown and deliberate socket-reset tests exist to check exactly that.

Testing a world you cannot eyeball

The test suite covers snapshots, moves, cache eviction and re-fetch, cross-board quiet moves, capture rules, duplicate and gap handling, two-client fan-out, socket teardown and failed writes. The load profiles open 40–80 active clients plus a few silent ones, subscribe them to 25 × 25 windows, and issue hundreds of snapshots and moves while checking every event frame.

There is also a benchmark dashboard covering board indexing, packed pieces, protocol codecs, move validation and application, the ledger, the worker, snapshots and startup. At this point the project is less “chess” and more a small distributed system with a board-shaped workload.

What's next

The invariants are unusually easy to state — a move either applies or it does not; a capture only happens on the piece's home board; a snapshot plus subsequent moves equals the authoritative state. That makes the project a tempting target for some lightweight formal verification, which is the part I want to explore next.
