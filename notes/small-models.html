Small models, local loops

Building an overnight harness for local coding models, and steering a chat model by its neurons.

18 October 2026 5 min read Local models · Evaluation

Running models locally changes what you optimise for. Latency and token budgets stop being abstractions and become things you can feel. A few months ago I built two small setups to explore that: an overnight harness for coding problems, and a chat server that lets me intervene on individual neurons while a model is generating.

The model you planned to use is not always the model you can use

The original plan was a sweep on a 4B thinking model via Ollama. On this machine that build spent every budget I gave it — up to 3,072 tokens, at roughly 7.8 tokens per second — on chain-of-thought and never emitted a code block. An overnight comparative study was not feasible. Rather than quietly dropping the condition, the config records the deviation and the sweep moves to a 1.7B thinking-capable model at around 15 tokens per second, with a 3B coder as a secondary.

That is a useful lesson in evaluation design: a result from a model that never reaches the answer is not a result about prompting, it is a result about the harness. The budget has to be part of the experiment, not an implementation detail.

Strategies, execution, hidden tests

The harness compares a few conditions: a direct answer, an explicit plan before code, and variants that get to see failing public tests and repair the solution. Generated Python runs in a sandbox with time limits, a memory cap and network isolation. Public tests are visible to the model; a separate hidden suite is not. Every trial records the prompt, the raw generations, token counts, timings, test results and the exact configuration in SQLite.

The point is not to crown a winning prompt. It is to make the difference between “produced code” and “produced code that passes something it has not seen” visible, and to keep the cost of that distinction in the same table. Small models are sensitive to scaffolding, so a fair comparison needs the scaffolding to be explicit.

Steering a model at the neuron level

The second experiment is a local chat server for Qwen3.5-4B that exposes a few intervention rules — layer, neuron and a signed value. At each forward pass it hooks the MLP intermediate activations and scales the selected neurons before the rest of the block runs.

It is a deliberately blunt instrument. Two rules at layers 13 and 14 are enough to change the texture of a response, and having a live UI makes it possible to compare steered and unsteered generations without editing a script between prompts. The engineering is mostly bookkeeping: one generation at a time on CPU in float32, clear state, and a lock so the hook cannot be mutated mid-token.

What I took away

Local models are less about raw capability and more about the loop around them: budgets, execution feedback, and a way to compare runs honestly. The model is one component; the harness is what turns its output into evidence. The same is true of steering — the interesting question is not whether a neuron changes the answer, but whether the change is stable, measurable and worth the complexity.
