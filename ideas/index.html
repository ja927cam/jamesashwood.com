Things to chase.

Things I'd like to build or understand. None of these are commitments — they're notes to myself, kept in public in case they're useful to someone else. If one overlaps with something you're working on, I'd like to hear about it.

01

Evaluation as a first-class artefact

The gap between a demo and a product is usually an evaluation set. I'd like to build tooling that treats evals as versioned artefacts: prompts, expected outputs, rubrics, cost and latency budgets in one place, runnable on every change. The interesting design question is making it easy enough that people write the cases before they ship.

  • LLMs
  • Evaluation
  • Tooling

02

Verification as an LLM safety net

Generated code is persuasive, not correct. If a model has to emit a type, a proof obligation or a test it cannot rewrite, the burden shifts from trusting the output to checking it. I want to understand where lightweight verification — types, contracts, property tests — catches real failures without making the system unusable. The hard part is usually the interface, not the theorem.

  • Formal methods
  • Machine learning
  • Compilers

03

A compiler for spreadsheet intent

Spreadsheets are the world's most popular programming environment and one of the least understood. A model can read the grid, but the meaning lives in formulas, formatting and convention. I'd like to build a small system that extracts intent from a workbook and emits a validated, reproducible transformation instead of another wall of text.

  • Structured data
  • LLM tooling
  • Compilers

04

Small models, sharp tools

Most tasks inside a business are narrow. A small local model with a constrained interface, good retrieval and a tight eval set can be cheaper, faster and more private than a general assistant. The interesting question is how much product quality comes from the model versus the tool around it — and whether "good enough" is a stable place to stand.

  • Local models
  • Product
  • Privacy

05

Tokenisation is a product decision

Token counts shape latency, cost and what fits in context, yet they are usually treated as an implementation detail. I'd like to collect examples where changing the representation — not the model — changed the economics of a feature, and turn that into a practical guide. Tables, logs, JSON and code all have different shapes of waste.

  • LLMs
  • Cost
  • Writing
Thinking
06

Telemetry for racing simulators

Racing simulators produce high-frequency, multi-channel telemetry; most of it is thrown away or plotted badly. I'd like a small pipeline that captures a stint, aligns it with setup changes and produces a driver-readable summary. The same problems — sampling, alignment, missing data — show up in any real-time system.

  • Simulation
  • Data
  • Motorsport
